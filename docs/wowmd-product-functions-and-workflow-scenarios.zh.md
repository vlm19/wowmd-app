# wowMD 产品功能与典型应用场景说明

## 1. 产品定位

wowMD 是面向长 Markdown 阅读与审阅的本地优先工具集。它不是普通的 Markdown 转换器，也不是云端文档平台，而是一层介于“AI 或人工产出的 Markdown 草稿”和“最终要交付、归档、复核的内容”之间的审阅工作层。

当前产品由两个互补部分组成：

- **wowMD Chrome Extension**：免费浏览器插件，聚焦 GitHub 上的公开 Markdown 阅读。它让 README、`.md`、`.markdown` 文件页更容易导航、折叠和阅读。
- **wowMD Pro Web App**：本地优先的 Web 应用，聚焦本地 Markdown 文件、结构化阅读、语义标注、笔记、版本延续和多种导出。

两者的边界很清晰：插件负责“在 GitHub 上快速打开并读懂长 Markdown”，Web App 负责“把 Markdown 当作可审阅、可标注、可交付的工作对象处理”。

## 2. 核心价值

wowMD 解决的主要问题是：长 Markdown 在默认浏览器、GitHub 页面或普通编辑器里很容易失去结构感。用户需要频繁滚动、查找标题、理解代码块、处理宽表格、记录疑问，并把审阅结果交给人或 AI 继续处理。

wowMD 的核心工作流可以概括为：

1. **打开**：从 GitHub 或本地打开 Markdown。
2. **阅读**：通过目录、折叠、搜索、代码高亮、表格滚动和主题设置理解内容。
3. **判断**：用四种语义审阅类型标记选中的文本。
4. **沉淀**：把标注、笔记、建议替换、章节上下文保存在浏览器本地。
5. **交付**：导出 HTML、Obsidian 可读 Markdown、备份 JSON 或 AI 工单 JSON。

这条路径把“读完一篇文档”升级为“完成一次可追踪、可交付的审阅”。

## 3. Chrome 插件功能

### 3.1 支持的内容

Chrome 插件面向公开 GitHub Markdown 页面：

- 公开仓库的 README 页面。
- 公开仓库中的 `.md` 文件页。
- 公开仓库中的 `.markdown` 文件页。

插件不处理本地文件，不处理私有仓库集成，不处理 Issues、Pull Requests、Wiki 页面或非 GitHub 网站。它也不包含标注、总体审阅地图、版本延续或导出功能，这些属于 Web App。

### 3.2 阅读增强

插件的目标是把 GitHub 原生 Markdown 页面变成更专注的阅读视图：

- **结构化目录**：根据标题生成目录，帮助用户快速判断文档层级并跳转。
- **章节折叠**：可折叠大型章节，减少长文档的滚动负担。
- **代码块优化**：提供更清晰的代码阅读体验，包括语法高亮和可读间距。
- **宽表格处理**：让宽表格在内部横向滚动，避免破坏整页布局。
- **长 README 阅读模式**：把仓库说明、技术文档、配置说明、安装步骤等内容整理为更适合阅读的界面。

### 3.3 隐私边界

插件设计为打开和阅读工具：

- 不收集个人信息。
- 不上传文档内容到第三方服务。
- 不做 AI 摘要、云端分析或远程配置。
- 插件仅在用户触发阅读增强时，在浏览器本地处理当前页面内容。

### 3.4 插件适合的场景

插件最适合低摩擦的 GitHub 阅读：

- 查看一个开源项目 README，快速理解安装方式和功能范围。
- 阅读框架、SDK、CLI 工具的长文档。
- 浏览仓库里的设计说明、架构说明或变更记录。
- 临时查找命令、参数、表格信息和章节内容。

插件提升效率的方式主要是减少“找位置”和“恢复上下文”的时间。用户不需要在 GitHub 原始页面里反复滚动，而是通过目录、折叠和更好的代码/表格布局快速定位重点。

## 4. Web App 功能

### 4.1 本地 Markdown 打开与导入

Web App 面向更完整的审阅工作：

- 打开本地 `.md` 和 `.markdown` 文件。
- 支持通过文件选择器或拖拽打开文档。
- 可从插件传入的公开 GitHub raw URL 导入 Markdown。
- 只允许抓取 `https://raw.githubusercontent.com/...` 形式的导入 URL。
- 将导入的 GitHub Markdown 保存为浏览器本地文档副本，并可通过 `/app/reader/:docId` 恢复。
- 内置示例文档可用于体验，不启动真实试用消耗。

Web App 不会上传用户打开的 Markdown。阅读、标注、导出、试用状态和本地存储都在浏览器中完成。

### 4.2 结构化阅读

Web App 的阅读区面向长技术文档和 AI 生成内容：

- **标题目录**：根据 Markdown 标题生成目录。
- **滚动跟随**：目录可辅助定位当前阅读位置。
- **H2 折叠**：大型二级章节可折叠，便于聚焦当前段落。
- **全文搜索**：支持匹配计数、上一个/下一个结果跳转。
- **代码块渲染**：使用语法高亮，并支持代码块复制。
- **表格渲染**：宽表格保持可用，通过内部滚动减少布局破坏。
- **链接与图片**：渲染常见 Markdown 链接和图片；本地相对资源在浏览器允许时尽量解析。
- **主题与字号**：支持浅色、深色等阅读主题，并可调整正文和目录字号。
- **独立滚动区域**：目录、正文和笔记区分别滚动，减少互相干扰。

这些能力让长 Markdown 更像一个可操作的阅读工作台，而不是一整块需要手动翻找的文本。

### 4.3 四种语义审阅类型

Web App 的标注不是单纯换颜色，而是记录用户对文本的判断。当前核心类型为：

| 类型 | 含义 | 典型动作 |
|---|---|---|
| Clarify / 澄清 | 这里需要解释、补充背景或说清楚 | 让 AI 或作者补充说明，但不改变核心事实 |
| Dispute / 争议 | 这里可能有误、需要复核或修正 | 要求检查事实、逻辑或实现细节 |
| Important / 重点 | 这里是关键点，应保留并强调 | 在后续总结、交付或复盘中优先关注 |
| Confirmed / 已确认 | 这里已审过且可信 | 保持原样，减少重复复核 |

用户选中文本后，可以通过浮动工具栏选择类型，添加短笔记，或写入建议替换文本。建议替换不会直接改动源 Markdown，它只会作为审阅意见进入后续导出。

### 4.4 标注锚定与跨版本延续

Web App 保存标注时，不只保存颜色或位置，还会记录：

- 文档指纹。
- 命中的原文 quote。
- 前后文 prefix / suffix。
- 所在标题路径 heading path。
- 位置 fallback。
- 标注类型。
- 笔记内容。
- 建议替换。
- 创建和更新时间。

这样做的目的，是在文档轻微改动后尽量把标注重新锚定到正确段落。如果无法自动恢复，用户仍可通过笔记面板中的定位和查找能力手动找回上下文。

### 4.5 笔记面板

笔记面板是审阅工作的控制台：

- 展示全部标注和笔记。
- 按类型过滤标注。
- 点击标注回到原文位置。
- 管理疑问、争议、重点和已确认内容。
- 为导出 HTML、备份 JSON、Obsidian Markdown 和 AI 工单提供数据来源。

它适合在阅读后快速复盘：“我哪里不理解？哪里有争议？哪些内容必须保留？哪些段落已经确认？”

### 4.6 Overall Review Map

Overall Review Map 把类型化标注整理成文档级审阅总览：

- **Coverage** 展示已有多少章节完成类型化审阅。
- **Review confidence** 展示 Confirmed 与 Important 判断所占比例。
- **Risk focus** 标出下一步需要重点处理的章节。
- **Document Overview** 展示每个章节的标注类型组合。
- **Needs attention** 解释为什么特定章节需要优先审阅。

它不会判断文档本身的质量，也不会生成 AI 摘要。它呈现用户当前的审阅状态，并支持直接返回对应章节继续处理。

### 4.7 导出能力

Web App 的导出不是附属功能，而是审阅闭环的最后一步。

#### HTML Export

面向人阅读：

- 导出单个离线可读 HTML 文件。
- 保留文档结构、目录、标题锚点、正文、代码块、表格、链接、图片、标注和笔记。
- 可用任意浏览器打开。
- 不包含 App 运行时、追踪脚本或授权逻辑。

典型用途是给同事、客户、未来的自己或评审者一个可直接打开的阅读副本。

#### Reviewed Markdown for Obsidian

面向知识管理：

- 生成一个新的 `.md` 副本。
- 用 Obsidian 可读的 callout、标签和属性保留 wowMD 审阅痕迹。
- 不覆盖原文件。
- 不直接应用建议替换。
- 不调用 AI。

典型用途是把审阅后的文档放入 Obsidian、个人知识库或长期项目资料夹。

#### Backup JSON

面向备份和迁移：

- 导出原始标注数据。
- 用于备份、重新导入或程序化处理。
- 不适合作为直接交给 AI 的完整上下文，因为它主要保存标注本身。

典型用途是避免浏览器本地数据丢失，或在后续版本中恢复审阅状态。

#### Ticket JSON

面向 AI 或人工编辑：

- 包含文档快照。
- 包含四种标注类型的处理说明。
- 包含每条标注的章节路径、命中文本、前后文、笔记和建议替换。
- 可以作为“工作单”交给 AI 或编辑者逐条处理。

典型用途是把“我读完后的判断”转成“AI 可以执行的修订任务”。这也是 wowMD 区别于普通阅读器和普通转换器的关键功能。

### 4.8 本地存储与隐私

Web App 使用浏览器站点数据，而不是普通缓存：

- 已保存的标注主要保存在 `localStorage`，并有 IndexedDB 相关 fallback / store 逻辑。
- 导入的 GitHub Markdown 副本保存在 IndexedDB。
- 本地文件本身通常不作为完整文档副本长期保存，标注会按文档指纹和会话信息关联。
- 工具栏中尚未点击 Save 的临时输入不等于已保存数据。

需要明确的边界：

- 普通刷新、关闭再打开浏览器时，已保存标注通常可以保留。
- 清除站点数据、使用隐身模式、更换浏览器或浏览器配置、浏览器存储被回收，可能导致本地数据丢失。
- 用户仍应导出重要标注或成品文档作为备份。
- 浏览器本地数据仍可能包含敏感信息，例如文档片段、笔记、建议替换、源 URL、标题和版本信息，应按敏感数据管理。

## 5. 插件与 Web App 的协同

插件和 Web App 可以理解为同一产品家族里的两个阶段：

| 阶段 | 工具 | 用户目标 |
|---|---|---|
| 快速阅读 | Chrome Extension | 在 GitHub 上快速读懂公开 Markdown |
| 深度审阅 | Web App | 打开本地或导入文档，进行标注、笔记、导出 |
| 交付归档 | Web App | 生成 HTML、Obsidian Markdown、Backup JSON 或 Ticket JSON |

典型路径：

1. 用户在 GitHub 上看到一个很长的 README 或设计文档。
2. 用插件进入更清晰的阅读视图，快速判断是否值得深入处理。
3. 如果需要做标注、形成审阅意见或交给 AI 修订，则进入 wowMD Pro。
4. 在 Web App 中完成标注、笔记、Overall Review Map 检查和导出。

这种分工避免插件变重，也避免用户每次只是浏览 GitHub 文档时被迫进入完整工作台。

## 6. 典型应用场景

### 场景一：开发者阅读大型开源项目 README

用户目标：

- 快速理解项目用途、安装步骤、配置方式和限制。
- 找到关键命令、API、兼容性说明或注意事项。

推荐工作流：

1. 在 GitHub README 页面使用 Chrome 插件打开阅读视图。
2. 通过目录先看整体结构。
3. 折叠暂时不相关的章节。
4. 在代码块和表格中查找安装命令、参数和环境要求。
5. 如果只是临时阅读，到插件即可结束。
6. 如果需要形成长期笔记，则把相关 Markdown 放入 Web App 深度处理。

效率提升：

- 减少在 GitHub 原始页面里反复滚动的时间。
- 通过目录快速判断文档是否覆盖当前问题。
- 宽表格和代码块更容易阅读，降低复制错误和漏看参数的概率。

### 场景二：产品经理审阅 AI 生成的产品规格

用户目标：

- 判断 AI 生成的规格是否完整、准确、可执行。
- 标出需要澄清、存在争议、必须保留和已经确认的内容。
- 生成一份可交给 AI 继续修订的工作单。

推荐工作流：

1. 在 Web App 打开本地产品规格 Markdown。
2. 用目录和折叠先扫一遍整体结构。
3. 对模糊段落标记为 Clarify。
4. 对可能错误的范围、约束、用户故事或商业假设标记为 Dispute。
5. 对必须进入最终方案的内容标记为 Important。
6. 对已经确认无误的段落标记为 Confirmed。
7. 打开 Overall Review Map，优先处理审阅缺口、风险重点以及争议和澄清集中的章节。
8. 导出 Ticket JSON，粘贴给 AI，让它按标注逐条修订完整文档。
9. 必要时导出 HTML 给团队成员阅读。

效率提升：

- 把“读文档时脑中的判断”转为结构化数据。
- 避免给 AI 只写一句“帮我改好”，改为提供带上下文、类型和建议替换的工作单。
- 团队评审时可直接看到哪些地方有争议，减少会议中重新读全文的时间。

### 场景三：工程师审阅技术实现方案

用户目标：

- 检查架构方案、接口设计、迁移步骤、风险项是否合理。
- 把需要复核的技术点交给作者或 AI 修改。

推荐工作流：

1. 在 Web App 打开实现方案 Markdown。
2. 用全文搜索定位关键模块、API、数据库表、配置项。
3. 对错误假设、缺失边界条件、性能风险标记 Dispute。
4. 对关键不变量、迁移顺序、安全要求标记 Important。
5. 在笔记中写明原因或建议替换。
6. 导出 Ticket JSON 给 AI 或作者处理。
7. 导出 HTML 作为评审记录。

效率提升：

- 技术评审不再停留在口头意见或零散评论里。
- 每条问题都带章节路径、原文和上下文，减少沟通成本。
- 最后交付的是可执行修订任务，而不是模糊反馈。

### 场景四：知识管理用户整理长文档到 Obsidian

用户目标：

- 阅读一篇长 Markdown，并把有价值的部分沉淀到个人知识库。
- 保留重点、疑问和个人判断。

推荐工作流：

1. 在 Web App 打开本地 Markdown。
2. 用 Important 标记核心观点。
3. 用 Clarify 标记日后需要补充理解的段落。
4. 用 Confirmed 标记已验证信息。
5. 导出 Reviewed Markdown for Obsidian。
6. 把新生成的 `.md` 文件放入 Obsidian vault。

效率提升：

- 不需要手动复制摘录、补标签和写旁注。
- 原文保持不变，审阅后的副本单独归档。
- 后续在 Obsidian 中仍能看到 wowMD 标注形成的上下文。

### 场景五：团队把审阅结果交付给非技术成员

用户目标：

- 让非技术成员阅读一份长 Markdown 的整理版。
- 避免要求对方安装编辑器、理解 Markdown 或进入代码仓库。

推荐工作流：

1. 在 Web App 完成阅读、标注和笔记。
2. 使用 HTML Export 导出离线 HTML 文件。
3. 将 HTML 文件发给团队成员或归档到项目资料。
4. 对方直接用浏览器打开，查看目录、正文、重点和笔记。

效率提升：

- 接收方无需安装 Markdown 工具。
- 文档结构、重点和笔记在一个文件里保留。
- 比截图、聊天记录或零散摘录更容易复查。

### 场景六：把 AI 长输出变成可执行修订闭环

用户目标：

- AI 生成了很长的方案、报告或说明，但质量参差不齐。
- 用户希望自己负责判断，AI 负责执行修订。

推荐工作流：

1. 把 AI 输出保存为 Markdown。
2. 在 Web App 中打开。
3. 用户只做高价值判断：澄清、争议、重点、确认。
4. 对需要修改的地方写建议替换。
5. 导出 Ticket JSON。
6. 把 Ticket JSON 和提示词一起给 AI，让 AI 根据用户标注输出修订后的完整 Markdown。
7. 再把修订稿导入 Web App 复核，必要时继续下一轮。

效率提升：

- 用户不需要逐句重写文档。
- AI 不再凭空猜测哪些地方要改，而是按用户标注执行。
- 标注可以跨版本尝试重新锚定，减少多轮修订时的重复工作。

### 场景七：迭代 Agent Skill 与工作流说明

用户目标：

- 改进 `SKILL.md`、提示词指南、agent instruction 文件或工具工作流文档。
- 让指令集更准确、更少歧义，并且更容易被 AI agent 正确执行。
- 保留已经验证过的规则，同时找出触发条件不清、工具顺序有问题、失败处理缺失、验收标准薄弱的地方。

推荐工作流：

1. 在 Web App 中打开 skill 或 instruction Markdown。
2. 用目录检查整体结构：触发条件、必用工具、执行顺序、约束、fallback 行为和验证步骤。
3. 对模糊或边界不足的规则标记为 Clarify。
4. 对与真实工具行为、产品边界或既往失败经验冲突的规则标记为 Dispute。
5. 对不可弱化的约束、安全规则和已经验证有效的工作流标记为 Important。
6. 对已经确认无误的说明标记为 Confirmed，避免重写时被意外改弱或删除。
7. 在笔记中写具体修改意见或建议替换文本。
8. 用 Overall Review Map 找出审阅缺口以及歧义和冲突最密集的章节。
9. 导出 Ticket JSON，让 AI 按照这些类型化审阅意见修订 skill。
10. 再用 wowMD 打开修订后的 Markdown 复审，确认后再提交回 repo。

效率提升：

- Skill 迭代从零散改提示词，变成有结构的审阅闭环。
- 重要约束和已验证规则在重写过程中保持可见。
- 歧义、矛盾和缺失边界会绑定到精确原文位置。
- AI 收到的是段落级修改指令，减少改错规则、漏掉关键约束或泛化重写的概率。
- 跨版本锚定可以帮助审阅者比较旧版和新版 skill，不必每轮都从头开始。

## 7. 工作流效率提升总结

wowMD 的效率提升不是来自“自动替用户判断”，而是来自把阅读、判断和交付连接起来：

- **更快定位**：目录、搜索、折叠和独立滚动让长文档更容易导航。
- **更少上下文丢失**：标注记录 quote、前后文和标题路径，不只是保存颜色。
- **更清晰的审阅语义**：四种类型把“这里有问题”拆成可执行判断。
- **更短的交付链路**：HTML 给人读，Reviewed Markdown 给 Obsidian，Backup JSON 给自己备份，Ticket JSON 给 AI 或编辑执行。
- **更安全的默认方式**：本地优先，不上传文档，不直接修改源文件。
- **更适合 AI 协作**：用户负责审阅和判断，AI 负责按结构化工单修订。
- **更可靠的指令迭代**：对于 skills、prompts 和 workflow documents，已确认约束、争议规则和建议重写都会绑定到精确原文，降低迭代时丢失关键规则的风险。

## 8. 当前边界与非目标

当前版本应保持聚焦，不把产品扩展成过重的平台：

- 不做云同步。
- 不做账号优先的文档平台。
- 不做团队协作标注。
- 不做企业版授权系统。
- 不做私有仓库深度集成。
- 不做批量多文件项目处理。
- 不在 v1 中承诺 AI 摘要、翻译或自动重写。
- 不让插件承担 Web App 的深度审阅和导出职责。
- 不直接修改用户源 Markdown，除非未来明确设计写回功能。

这些边界保证 wowMD 的核心体验保持清晰：打开长 Markdown，读懂结构，做出判断，并把结果交付给人、知识库或 AI。
