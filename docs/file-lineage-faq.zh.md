# 文件谱系关联 FAQ

状态：Implemented v1 功能说明
最后更新：2026-06-07

## 什么是文件谱系关联？

文件谱系关联用于回答：“当前打开的 Markdown，是否是某份已审阅文档的后续版本？”

它让 wowMD 能够在文件被重命名、移动、手动编辑、导入 Obsidian，或经 Ticket JSON 交给 AI 修订后，发现可能的版本关系，并在用户确认后迁移标注和版本历史。

## 为什么不能继续用文件名判断？

文件名不是稳定身份。

- 用户可能只是在文件名中增加 `v2`、日期或 `reviewed`。
- 两份无关文档可能使用同一个文件名。
- 文件进入 Obsidian Vault 后可能被重命名或移动。

因此文件名只能作为提示用户的弱证据，不能作为自动加载标注的主键。

## wowMD 将如何识别同一文档家族？

wowMD 为文档家族分配稳定的 `lineageId`，为每个正式版本分配独立的 `documentId`，并通过 `parentDocumentId` 记录直接父版本。

这些 ID 是随机且不可读的，不包含文件名、路径、用户名或设备信息。

谱系元数据中的 `originalFilename` 是一个例外：它用于向用户展示来源文件名，因此会随 Markdown 一起流转。文件名可能包含姓名、项目代号等敏感信息；保存或分享 reviewed copy 前，应检查并按需要修改文件名。

## 为什么把谱系信息放在 Markdown 底部？

底部 HTML 注释块能够随 Markdown 一起移动、重命名和备份，避免 sidecar JSON 丢失或增加文件管理负担。

普通 Markdown 阅读器和 Obsidian 阅读模式不会显示该注释。wowMD 会在渲染、正文哈希和标注定位时排除它。

## wowMD 会在打开文件时修改源文件吗？

不会。

打开、检测、建立候选关系和重新定位标注都不能修改源文件。只有用户明确执行 `Save reviewed copy` 或导出操作时，wowMD 才能把谱系元数据写入新生成的 Markdown 文件。

## 原始文件没有底部元数据怎么办？

原始文件仍可正常打开。

wowMD 可以在浏览器本地为它创建身份记录，并使用内容哈希、结构、标题和文件名寻找候选关系。但这些只能形成提示，必须由用户确认。

直到用户显式保存新副本，谱系身份才会进入可携带的 Markdown 文件。

## 用户手动编辑了文件会怎样？

如果文件保留有效的 `lineageId`，wowMD 会把它视为同一文档家族中的“外部编辑候选版本”。

当当前正文哈希与元数据记录不一致时，wowMD 会提示内容已在外部变化，并预览标注结果：

- 精确定位；
- 根据上下文定位；
- 存在多个候选位置；
- 无法找到。

只有用户确认后，当前文件才会关联到原谱系。wowMD 不会自动更新源文件中的元数据。

## AI 根据 Ticket JSON 生成新 Markdown，如何关联原文？

Ticket JSON 将承担来源凭证角色。

生成工单时，wowMD 会记录原始文档的 `lineageId`、`documentId`、正文哈希和 `ticketId`。AI 输出的新 Markdown 应携带：

- 原文的 `lineageId`；
- 新版本的 `documentId`；
- 指向原文的 `parentDocumentId`；
- 对应工单的 `sourceTicketId`。

即使原始 Markdown 没有底部元数据，只要 AI 输出保留 `parentDocumentId`，wowMD 也可以通过浏览器本地的原文记录找到父版本，并提示用户确认关系。独立导入 Ticket JSON 并直接建立候选关系属于后续能力。

## 如果 AI 删除了元数据怎么办？

当前 v1 会优先读取 AI 结果中保留的 `parentDocumentId`、`lineageId` 和 `sourceTicketId`。如果 AI 删除了这些信息，wowMD 只能使用内容结构和标注可重新定位比例形成弱候选提示。

独立导入 Ticket JSON 并把它作为强候选证据属于后续能力。即使未来实现，也仍然必须由用户确认，不能自动建立关联。

## Ticket JSON 是否等于标注备份？

不等于。

- Backup JSON 用于保存和重新导入标注数据。
- Ticket JSON 用于把审阅判断交给 AI 或编辑执行，同时提供修订来源凭证。
- Markdown 底部谱系元数据用于让版本身份随文件流转。

三者用途不同，不应互相替代。

## wowMD 会自动搜索当前目录中的母文件吗？

浏览器不能在未经授权的情况下扫描用户目录。

如果用户通过目录选择器授予访问权限，未来可以在该目录中寻找候选文件。当前 v1 只搜索浏览器本地已登记的文档和用户主动打开的文件。

无论是否找到母文件，都必须由用户确认关联。

## 会记录设备信息吗？

不会记录真实设备名称、用户名、路径、硬件 ID 或 IP 地址。

可选的 `installationId` 只是本地随机 ID，用于辅助判断来源，可以重置，也不能用来识别真实设备或用户。

## 内容哈希能直接证明两个文件相关吗？

不能。

相同正文哈希只能说明正文相同，不代表两个文件必然属于同一工作流。正文变化后哈希也会变化。

哈希适合验证内容状态和检测外部编辑；稳定谱系 ID 与 Ticket 来源才是更可靠的关联证据。

## 内容相似度会自动关联文件吗？

不会。

内容相似度、标题结构、文件名和保存时间都只能用于发现候选。它们可能产生误判，因此不能自动迁移标注或合并历史。

## 用户拒绝关联后会怎样？

文件会作为新文档打开，不会迁移候选版本的标注，也不会建立正式父子关系。

wowMD 会保留一个浏览器本地的“待复核关系”，用户之后可以从文件菜单重新打开候选关系、查看差异并确认。该待复核记录不会写入 Markdown 文件，也不会被当作正式谱系。

## 无法重新定位的标注会丢失吗？

不会。

无法可靠定位的标注必须保留在待处理列表中。用户可以查看原引用、上下文和父版本位置，并手动重新定位或明确删除。

## Obsidian 如何受益？

谱系元数据跟随单个 Markdown 文件进入 Vault，不需要额外管理 sidecar 文件。

Obsidian 原生会保留 HTML 注释，但不会主动理解谱系。未来的 wowMD Obsidian 插件可以索引这些字段，展示父版本、来源 Ticket、修改时间和可迁移标注。

## 元数据会不会污染 Markdown？

在正常阅读模式下不会显示，但在源码模式中可见。

它是一个明确、可删除、版本化的 HTML 注释块。删除后文档仍然有效，只是失去一部分可携带的谱系证据；浏览器本地历史和 Ticket JSON 仍可能帮助恢复关系。

## 这些 ID 能证明文件可信或由某人创建吗？

不能。

协议 v1 的 ID 用于版本关系发现，不是数字签名。任何文本编辑器都能修改这些字段，所以 wowMD 必须结合本地记录、Ticket JSON 和用户确认使用，不能把它描述为作者认证或安全签名。

## 最可靠的关联顺序是什么？

推荐顺序：

1. 已知 `sourceTicketId`、`parentDocumentId` 和匹配的 `lineageId`；
2. 已知 `lineageId`；
3. 相同正文哈希；
4. 内容结构、标题、文件名和时间等弱候选证据；
5. 没有可靠候选时作为新文档打开。

所有关联最终都由用户确认。
